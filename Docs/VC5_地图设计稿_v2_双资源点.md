# VC5 地图设计稿 v2（双资源点版）

> **版本**: v2.0
> **日期**: 2026-05-24
> **设计目标**: 将每局地块从 3 个调整为 2 个，适配每玩家最多 3 英雄的设定

---

## 一、设计决策

### 1.1 为什么从 3 个改为 2 个

| 考量维度 | 3 地块 | 2 地块 |
|---------|--------|--------|
| **英雄数量** | 每人 3 英雄 | 每人 3 英雄 |
| **争夺分配** | 每人平均抢 1.5 个 → 总有 1 个成为焦点 | 每人平均抢 1 个 → 2 个都是焦点 |
| **行动力消耗** | 需要分散兵力到 3 个位置 | 兵力更集中，争夺更激烈 |
| **决策复杂度** | 3 个地块的优先级排序 | 2 个地块的取舍更清晰 |
| **对抗强度** | 可能出现"各占各的"和平局面 | 必然围绕地块产生直接冲突 |

**核心结论**：2 个地块 + 3 个英雄 = 每个地块都值得全力争夺，对抗更紧凑。

## 二、地块分布规则

### 2.1 棋盘坐标系

```

y=2  [1,2] [2,2] [3,2] [4,2] [5,2] [6,2] [7,2] [8,2] [9,2] [10,2]
y=3  [1,3] [2,3] [3,3] [4,3] [5,3] [6,3] [7,3] [8,3] [9,3] [10,3]
y=4  [1,4] [2,4] [3,4] [4,4] [5,4] [6,4] [7,4] [8,4] [9,4] [10,4]
y=5  [1,5] [2,5] [3,5] [4,5] [5,5] [6,5] [7,5] [8,5] [9,5] [10,5]
```

### 2.2 双地块分区方案

将棋盘分为 **左半区** 和 **右半区**，2 个地块分别从两个半区各选 1 个：

| 区域 | 坐标范围 | 说明 |
|------|---------|------|
| **左区（L）** | x: 1-5, y: 1-5 | 棋盘左半部分 |
| **右区（R）** | x: 6-10, y: 1-5 | 棋盘右半部分 |

### 2.3 地块位置生成算法

```
GenerateTilePositions():
  1. 从左区（x:1-5）随机选取候选位置集合
  2. 从右区（x:6-10）随机选取候选位置集合
  3. 排除英雄初始部署位置
  4. 在候选集合中选择满足最小距离约束的位置
  5. 为每个位置分配地块类型
```

**距离约束**：
- 2 个地块之间的六边形距离 >= 4（确保不会过于集中）
- 地块不与英雄初始部署位置重叠
- 地块优先分布在 y=2~4 的中间行（避免边缘死角）

## 三、地块类型选取规则

### 3.1 选取机制

从 9 种地块候选池中随机选取 **2 种**（不重复），分配到 2 个位置上。

```
GenerateTileTypes():
  1. 定义 9 种地块类型的候选池
  2. 从候选池中随机选取 2 种（不重复）
  3. 将选出的 2 种地块随机分配到左区和右区的位置上
```

### 3.2 选取概率

| 概率项 | 数值 |
|--------|------|
| 每种地块被选中的概率 | 2/9 ≈ 22.2% |
| 特定组合出现的概率 | 1/C(9,2) = 1/36 ≈ 2.8% |
| 出现得分地块的概率 | 1 - C(8,2)/C(9,2) = 8/36 ≈ 22.2% |

## 四、地块效果数值调整

### 4.1 调整原则

从 3 个地块减少到 2 个后，每个地块的影响力需要适当增强，以保证地块争夺的价值不变。

### 4.2 数值调整对比

| 地块类型 | 原3地块数值 | 新2地块数值 | 调整理由 |
|---------|-----------|-----------|---------|
| **T01 得分地块** | 每回合 +1 分 | 每回合 +1 分 | 不变，得分本身就是核心价值 |
| **T02 觉醒加速** | 觉醒进度 +1 | 觉醒进度 **+25%（向上取整）** | 改为百分比，各阶段效果可量化 |
| **T03 行动干扰** | 麻痹 1 个单位 | 麻痹 1 个单位 | 不变，控制效果不叠加 |
| **T04 法力源泉** | 每回合 +1 法力 | 每回合 +1 法力 | 不变 |
| **T05 战斗祭坛** | 攻击力 +1 | 攻击力 +1 | 不变 |
| **T06 生命圣泉** | 恢复 2 生命 | 恢复 3 生命 | ↑ 提升，2个地块时回复价值更高 |
| **T07 风行之径** | 移动力 +1 | 移动力 +1 | 不变 |
| **T08 抽牌神殿** | 每回合抽 1 牌 | 每回合抽 1 牌 | 不变 |
| **T09 护盾堡垒** | 获得 2 护盾 | 获得 3 护盾 | ↑ 提升，2个地块时防御价值更高 |

**总结**：大部分地块效果保持不变，仅生命回复和护盾类地块小幅提升，因为减少地块后续航型策略的收益自然降低，需要补偿。

## 五、地块争夺策略分析

### 5.1 双地块的核心博弈

2 个地块的争夺比 3 个地块更紧凑，核心博弈如下：

```
双地块争夺决策树：

              开局观察 2 个地块
                    |
          +---------+---------+
          |                   |
     两个地块价值相近      一个价值明显更高
          |                   |
    分兵 vs 集中          全力争夺高价值地块
     |         |                |
  风险：    风险：          风险：
  分兵太薄  放弃一个        对手也去抢
```

### 5.2 3 英雄 vs 2 地块的兵力分配

| 策略 | 兵力分配 | 适用场景 | 风险 |
|------|---------|---------|------|
| **集中抢一** | 3 英雄抢 1 个地块 | 某个地块价值远高于另一个 | 放弃另一个地块 |
| **2+1 分兵** | 2 英雄抢主地块，1 英雄抢副地块 | 两个地块都有价值 | 主地块可能抢不过 |
| **1+1+1 游击** | 各 1 英雄骚扰 | 打消耗战 | 无法形成有效争夺 |
| **先抢后守** | 先集中抢一个，再转移 | 需要快速占领 | 转移期间可能被反抢 |

### 5.3 地块组合策略表

| 组合类型 | 示例组合 | 推荐种族 | 核心策略 |
|---------|---------|---------|---------|
| **双速攻** | 得分 + 战斗祭坛 | 龙族 | 集中抢战斗祭坛，用攻击力优势碾压得分 |
| **双成长** | 觉醒加速 + 法力源泉 | 黏黏/龙族 | 抢觉醒加速，快速完成觉醒后反推 |
| **双控制** | 行动干扰 + 护盾堡垒 | 黏黏 | 用控制拖延对方，慢慢叠粘液 |
| **攻防混合** | 得分 + 生命圣泉 | 风灵 | 用高机动抢得分，圣泉提供续航 |
| **资源压制** | 法力源泉 + 抽牌神殿 | 任意 | 长期占领积累资源优势 |
| **极端机动** | 风行之径 + 得分 | 风灵 | 高速抢分，对手追不上 |

### 5.4 不同种族的地块偏好

| 种族 | 最优选地块 | 次优选地块 | 核心思路 |
|------|-----------|-----------|---------|
| **黏黏** | 觉醒加速 | 行动干扰 | 加速觉醒 + 控制对手 |
| **龙族** | 战斗祭坛 | 得分 | 增强攻击力 → 抢分/击杀 |
| **风灵** | 风行之径 | 得分 | 高机动抢夺任意地块 |

## 六、地块与觉醒的联动

### 6.1 双地块对觉醒节奏的影响

| 场景 | 影响 |
|------|------|
| **觉醒加速地块出现** | 双地块时只有一个加速地块，争夺更激烈，拿到的一方觉醒优势巨大 |
| **无觉醒加速地块** | 纯靠自然积累，觉醒节奏回归基准线 |
| **得分地块出现** | 觉醒后强力英雄驻守得分地块，形成"觉醒→得分"正向循环 |

### 6.2 双地块的觉醒节奏修正

| 情况 | 觉醒节奏变化 |
|------|-----------|
| 持续占领觉醒加速地块 | 升华所需回合数减少约 25%（如从 16 回合缩短至 12 回合） |
| 丢失觉醒加速地块 | 回归自然节奏 |
| 对手占领觉醒加速地块 | 己方需要更快行动，否则觉醒差距拉大 |

### 7.2 地块生成逻辑更新

```csharp
private void GenerateTiles()
{
    game_data.tiles = new TileInstance[2];  // 改为 2 个

    // 定义左区和右区
    List<Slot> zone_left = new List<Slot>();   // x: 1-5
    List<Slot> zone_right = new List<Slot>();  // x: 6-10

    int p = Slot.GetP(0);
    for (int y = Slot.y_min; y <= Slot.y_max; y++)
    {
        for (int x = Slot.x_min; x <= Slot.x_max; x++)
        {
            Slot s = new Slot(x, y, p);
            if (x <= 5) zone_left.Add(s);
            else zone_right.Add(s);
        }
    }

    // 排除部署位置
    // ...（同原逻辑）

    // 优先选择中间行（y: 2-4）
    zone_left = zone_left.Where(s => s.y >= 2 && s.y <= 4).ToList();
    zone_right = zone_right.Where(s => s.y >= 2 && s.y <= 4).ToList();

    // 随机选取
    Slot slot_left = zone_left[random.Next(zone_left.Count)];
    Slot slot_right = zone_right[random.Next(zone_right.Count)];

    // 从 9 种中随机选 2 种
    List<TileType> all_types = new List<TileType>
    {
        TileType.Score, TileType.AwakeningBoost, TileType.Disruption,
        TileType.ManaSpring, TileType.BattleAltar, TileType.LifeSpring,
        TileType.WindPath, TileType.CardShrine, TileType.ShieldFortress
    };
    ShuffleList(all_types);

    game_data.tiles[0] = new TileInstance(all_types[0], slot_left);
    game_data.tiles[1] = new TileInstance(all_types[1], slot_right);
}
```

### 7.3 地块效果结算更新

```csharp
private void ResolveTiles()
{
    if (game_data.tiles == null) return;

    foreach (TileInstance tile in game_data.tiles)
    {
        Card occupant = game_data.GetSlotCard(tile.slot);
        if (occupant == null)
        {
            tile.owner_player_id = -1;
            tile.consecutive_holds = 0;
            continue;
        }

        int owner_pid = occupant.player_id;
        Player owner = game_data.GetPlayer(owner_pid);

        switch (tile.type)
        {
            case TileType.Score:
                owner.kill_count += 1;
                break;

            case TileType.AwakeningBoost:
                // 所有英雄觉醒进度 +25%（向上取整）
                // 例如：初醒条件 8 层 -> +2 进度；进阶条件 16 层 -> +4 进度
                break;

            case TileType.Disruption:
                TriggerDisruptionTile(owner, tile);
                break;

            case TileType.ManaSpring:
                owner.mana_max += 1;  // 临时增加
                break;

            case TileType.BattleAltar:
                // 占领方所有单位攻击力 +1
                break;

            case TileType.LifeSpring:
                // 恢复 3 生命（从 2 提升至 3）
                break;

            case TileType.WindPath:
                // 占领方所有单位移动力 +1
                break;

            case TileType.CardShrine:
                // 抽 1 张牌
                break;

            case TileType.ShieldFortress:
                // 获得 3 护盾（从 2 提升至 3）
                break;
        }

        // 更新占领信息
        if (tile.owner_player_id == owner_pid)
            tile.consecutive_holds++;
        else
            tile.consecutive_holds = 1;
        tile.owner_player_id = owner_pid;
    }
}
```

## 八、胜利条件与地块得分的平衡

### 8.1 当前胜利条件

胜利条件为 `kill_count >= 9`。

### 8.2 双地块下的得分分析

| 路线 | 所需条件 | 预计回合数 |
|------|---------|-----------|
| **纯击杀** | 击杀 3 个敌方单位（3×3=9分） | 8-12 回合 |
| **纯地块得分** | 占领得分地块 9 个回合（9×1=9分） | 9 回合（需全程占领） |
| **混合路线** | 击杀 + 地块组合 | 6-10 回合 |

### 8.3 双地块得分的影响

- **得分地块出现概率**：22.2%（2/9）
- **得分地块价值**：因为只有 2 个地块，得分地块的争夺更集中，占领难度更高
- **平衡性**：得分路线的难度从"分散兵力"变为"集中争夺"，整体平衡性更好

## 九、设计总结

### 9.1 双地块设计的优势

1. **争夺更集中**：2 个地块让每个地块都成为必争之地，避免"各占各的"
2. **决策更清晰**：2 个地块的取舍比 3 个地块更直观
3. **对抗更激烈**：3 英雄 vs 2 地块，兵力分配成为核心决策
4. **节奏更紧凑**：减少地块后，游戏节奏更快，对抗更直接

### 9.2 与种族设计的配合

| 种族 | 双地块优势 | 双地块劣势 |
|------|-----------|-----------|
| **黏黏** | 控制地块后难以被抢走 | 机动性不足，转移慢 |
| **龙族** | 高攻击力容易抢夺和守住地块 | 缺乏机动性，可能抢不到 |
| **风灵** | 高机动性可以快速抢夺和转移 | 守住地块的能力较弱 |
