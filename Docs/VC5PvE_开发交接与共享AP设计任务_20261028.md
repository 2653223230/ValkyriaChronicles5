## 0. 新 agent 首先知道的事

1. **主线是 `Prototypes/VC5PvE`，继续这个工程；不要从仓库根 Unity 工程重做，也不要再建新工程。**

3. 当前代码交互：**先选棋子→选牌→点击最终目标**，支持把牌拖到最终目标。下一版用户要改成**卡牌拖给执行棋子**。这两者不能混为已经完成的同一个需求。
4. **下一步只做设计供用户审核。** 共享 AP、通用卡因执行者产生差异、弃牌保底，尚未实现；本交接不是实施授权。
5. **改代码前先修改对应文档；代码完成后再核对并维护文档。** 不能只更新交接日志而让卡面表、规则、提示文案继续失配。

## 2. 当前实际玩法基线（不要写成下一版）

- 玩家三人：守铃者9HP/3AP、星纹师5HP/2AP、回响医者6HP/2AP。**AP目前仍是个人资源**，每回合恢复，不跨回合存留。
- 基础移动花1AP：守铃者/星纹师最多1格，回响医者最多2格；当前不依赖卡牌。基础普攻花1AP、每人每回合一次；回响医者另有基础急救。下一版不能未经设计就沿用这些效率。
- 起始牌组7种17张：稳步推进×3、重攻击×3、掩护×3、破阵突入×2、星火印×2、贯星术×2、战术鼓舞×2。卡面/升级效果源在 `Rules/RuleData.cs`。
- 起手6张、每轮补至6张、未出手牌保留。正式流程使用演示起手；不能把它当作随机起手卡手率已经验证。回合首次行动前有一次换牌。
- **已有抽牌堆、弃牌堆、洗回与回收。** 不需要再次“新增墓地概念”；弃牌堆空、满手回收、回收选择中锁定操作已有实现。
- 三关：林地入口→双阵遗迹（护阵柱与绑定守卫）→钟庭守卫（双锚、首领减伤及区域震荡预告）。两次营地依次选棋子天赋、新卡奖励、单张牌升级/删除或允许的跳过；新卡包括接力打击、协防、回收战术。
- 当前距离/走位用四方向与曼哈顿距离；远程攻击检查格子中心视线，实体障碍遮挡，单位不遮挡。不要只用“职业允许”判断能否出牌，要检查费用、目标、距离、视线等完整合法性。
- 当前操作选定角色后保留行动者，不静默换人；死亡清空选择。卡牌和基本行动预览不改变真实状态，最终合法执行才扣资源。
- 当前破阵突入是先落点、再邻敌；首步不移动、不扣费。掩护须明确选自身；回收战术选牌确认才付费。Esc/右键取消。
- UI：头像队伍栏、HP条随血量绿→黄→红、AP蓝菱形、选中强调、可用牌上浮/不可用变暗、目标高亮、拖牌留槽淡出与从行动者发出的箭头、移动/伤害/状态预览。费用预览用将被扣除的AP点闪烁，不显示“AP2→1”。
- 不把“基础蓄势”“早期局内符印升级”“复杂卡组引擎灵感”当作现行规则；它们与后来已批准的三关天赋是不同提案。

典型调用链：`PrototypeFlow / CardHandView` → `CardAimResolver / ActionPlanner` → `BattleController.Preview` → `BattleState.Clone + BattleResolver`生成展示结果 → 最终输入触发`BattleController.Confirm`重新验证 → `BattleResolver`正式结算 → `BoardView/UnitView`动画、HUD刷新。

Rules是纯C#规则层；Runtime/UI处理Unity表现。程序集边界可看各层 `.asmdef`。Assets外的 `Tools/RuleChecks` 是辅助规则检查，不能替代Unity PlayMode/实机验证。

美术：原型 `Assets/Art/`、`Assets/Audio/`，以及 `THIRD_PARTY_NOTICES.md`/各资源SOURCE或许可文件；根目录 `img/`和旧工程角色素材是来源线索。优先复用已有素材和资源，别重复生成整套资产。用户想要精美明亮、日式二次元HD-2D；截图/灵感海报不是实机验收。

## 7. 下一轮任务：共享 AP + 通用卡的角色分工（用户方向，待设计审核）

### 7.1 已确认方向

1. 棋子不再分别拥有可花费AP，**全队共用行动资源**。用户初步设想全队约6–8AP，编队时每名角色贡献2–3点不等；具体数值与刷新规则未批准。
2. **卡牌是主要战斗行动与爽点来源。** 不希望好牌可用可不用、缺牌就依靠低效基础普攻硬熬；强大自主行动可以是以后养成成果，但不是新版本开局默认体验。
3. **一张牌尽可能给多名棋子用，但不同棋子执行有不同效果/战术价值**，玩家要选择同一张牌给谁最好。不是重新做三套互不通用的专属牌。
4. **交互明确改回“卡牌拖到执行棋子”。** 用户已澄清原话的笔误；需要目标/落点时再按牌型选择。下一版具体点击备选方式、预览和确认时机仍需设计，不能把10月22日的直接拖最终目标继续当新需求。
5. **角色保留自带基础移动。** 这只确认“不依赖抽到移动牌”；并未确认移动免费、独立移动点、每回合次数或距离。需提出方案。
6. 可提出**弃一张任意手牌+支付共享AP**执行基础行动的防卡手机制。这是候选，不是已经决定每种基础技能均可无条件使用。
7. 角色、牌面、数字和状态先保持简单，凸显核心魅力。尽量让玩家一眼看懂，避免过多选项/标记/资源种类。
8. 先出一版可审核设计，**不写游戏代码、不改场景/配置/正式牌表、不打包**。仍沿着现有三人、8×8、三关原型考虑兼容。

### 7.2 仍然有效的体验目标

- 靠站位与推进逐步获得有利局面；靠卡组调度连起组件；靠角色配合完成一次明显的爆发。
- **这轮先做准备，下一轮能够打出明显更强的一轮进攻。** 要写出准备成本、敌人回合风险和兑现收益，不能只给当回合连点伤害牌。
- 降低“抽一打一”。玩家应知道自己在筹备什么、缺什么、如何找到/生成/回收关键牌，而不是只有随机抽到好牌才有方向。
- 借鉴炉石/三国杀等易懂概念可以，但**废弃以游戏王/额外卡组体系作为玩家理解前提**。早期三套卡组复杂度过高，不回头堆检索/召唤/连锁层级。
- 同牌不同角色的差异应少而明确、与站位有关；避免把每张通用牌写成三段复杂角色专属说明，或让某一角色永远是最优执行者。

### 7.3 新 agent 应提交的审核稿

建议新建 `Docs/VC5PvE_共享AP与通用卡角色差异设计_待审核_20261028.md`，首行标注“未批准、未实现”。在现行规则及棋子卡牌文档只加候选入口与影响范围，不覆盖已实现表格。如用户另指定追加位置则服从。

需要给出一版明确推荐方案，而不只是抽象建议或大量备选：

- 一页核心规则：共享AP上限/来源/回合刷新/是否结转、手牌与弃牌、基础移动、保底动作、出牌步骤；明确哪些保留、哪些改动。
- 简单角色与卡组：建议先围绕三人和少量通用牌验证（数量由设计者论证，不是用户硬指定）。角色表写AP贡献、生命、移动及一句特色；牌表写费用、目标、游戏内描述、详细规则、使用者。
- **同牌对照**：至少挑2–3张关键通用牌，展示给不同角色时的效果/位置要求/收益；给出“此局面交给A更好，换个局面交给B更好”的具体例子。
- **两个连续回合实例**：列共享AP与手牌账本、准备动作、敌方威胁、次轮兑现；验证不是把全部AP永远灌给同一输出棋子，也不是免费检索回收无限循环。
- 防卡手：无合法攻击目标、全是防御/支援牌、关键角色倒下、共享AP耗尽、回收后满手等如何处理；弃牌保底不应在效率上长期压过正式牌。
- 交互说明：拖牌→合法执行者全身高亮→悬停显示该角色执行的具体差异→松手后的后续目标/落点选择→何时扣卡扣AP→取消。区分无后续目标的自用牌、需攻击目标的牌和复杂移动牌，尽量减少确认次数。
- 共享AP的视觉语义：全队池放哪里、卡牌费用蓝菱形怎样保留、头顶个人AP撤掉或改为什么。先写设计，不擅自制作重要UI或实现。
- 三关成长迁移：现有减费/抽牌/回收天赋哪些保留、简化或暂禁；是否把“强自主行动”留作成长收益。首版无需把全部旧天赋硬塞进去。
- 最后列出少量必须审核的决定，以及不确定/待试玩项。用户明确批准后才进入UI审核、文档先行、代码和验证阶段。

### 7.4 必须明确裁定的底层问题

- 每人贡献2–3AP会自然出现6–9，用户总体预期6–8：限制组合、统一上限、还是调整贡献？别未经说明就选定数值。
- 基础移动是否花共享AP？如果免费，用什么明确上限防止无限走位？此前基础移动大多数1格、少数2格、不一次3格的偏好仍应尊重，改动要显式提出。
- 棋子死亡是否降低共享AP上限、何时降低？防止越输越不能操作，也别暗中保留死亡角色继续行动。
- 共享AP是否按轮恢复、是否允许结转/补充？与低复杂度、连续出牌和跨回合筹备如何平衡？
- 如何避免远程输出角色独占全队AP？优先用射程、位置、简单角色特色和配合收益解决，不默认叠加多种硬性次数限制。
- 弃牌支付是否要二次选牌？能否让交互与正常拖牌统一？明确成本和取消边界，不只在规则里写一句“弃1牌”。

### 7.5 审核通过后才考虑的代码影响清单

共享资源不是把UnitState.Ap替换一个字段就结束：BattleState/Clone、ActionPlanner、BattleResolver、TurnRules、GrowthRules.CardCost及折扣触发、BattleController自动交接与回收锁、CardAimResolver合法性、PrototypeFlow交互阶段、三处个人AP展示、卡牌费用预览、关卡敌方节奏、旧测试断言都要对应调整。敌人目前不依赖玩家共享AP，不能机械统一敌我逻辑。

先设计清楚以上问题，再做实施计划；本节只是后续定位提示，不是现在可执行的代码任务。
